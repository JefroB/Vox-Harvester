# Code Review

## Core Principle

Code review catches what tests miss: design problems, security holes, unclear intent, and maintainability issues. Review is collaborative, not adversarial.

## What to Review

### Always check:
- **Logic correctness** — Does it do what it claims? Off-by-one errors, wrong conditions, missed cases
- **Security** — Injection vectors, unvalidated input, exposed secrets, missing auth checks
- **Edge cases** — Null/empty/zero inputs, concurrent access, failure paths
- **Error handling** — Are errors caught at the right level? Are error messages useful?
- **Naming & clarity** — Can someone unfamiliar understand this in 30 seconds?
- **Missing tests** — Is the new behavior tested? Are edge cases covered?

### Don't waste time on:
- Formatting/style (linters handle this)
- Personal preference with no functional difference
- Rewriting working code to match your style

## Severity Levels

Flag issues with clear severity:

- **Critical** — Must fix before merge. Logic bugs, security vulnerabilities, data loss risk, broken functionality.
- **Warning** — Should fix. Poor error handling, missing validation, unclear behavior, potential race condition.
- **Suggestion** — Nice to have. Better naming, slight simplification, additional test case.

## Review Process

1. Read the diff top-to-bottom. Understand the intent before judging implementation.
2. Check: does the change match its stated purpose? (commit message, PR description, task)
3. Identify the boundaries — where does user input enter? Where does data leave?
4. Trace the happy path, then trace the failure paths.
5. Look for what's NOT there: missing validation, missing error handling, missing tests.

## Giving Feedback

- Be specific: point to the exact line and explain the issue
- Explain WHY, not just "this is wrong" — what could go wrong?
- Offer a fix or direction, not just criticism
- Distinguish between blocking issues and suggestions
- If everything looks good, say so briefly — don't invent problems

## Anti-Patterns in Review

- ❌ Nitpicking style while missing a logic bug
- ❌ Rewriting the entire approach without explaining why the original fails
- ❌ "LGTM" with no evidence of actual review
- ❌ Blocking on opinions without technical justification
- ❌ Reviewing only the lines changed without understanding the surrounding context

## Feedback Loop: Updating Anti-Patterns

When reviewing code generated by the local Ollama subagent, if you discover a **new recurring pattern** that the model gets wrong:

1. **Fix the immediate issue** in the generated code
2. **Check if the pattern is already in `.kiro/skills/anti-patterns.md`**
3. **If it's NOT already documented**, add it:
   - Open `.kiro/skills/anti-patterns.md`
   - Add the new anti-pattern under the appropriate section (Concurrency, Resource Management, Error Handling, Data Structures, Async)
   - Include a ❌ WRONG example (what the model produced)
   - Include a ✅ CORRECT example (how it should be done)
   - Keep it concise — one pattern per entry
4. **Also add a note to `.kiro/steering/memories.md`** under the "Ollama / Local Models" section describing when/where this was discovered

### What qualifies as a "new recurring pattern"?

- You've seen the same mistake **twice or more** across different generations
- OR it's a **critical bug** (deadlock, data loss, security hole) even if seen only once
- NOT: one-off typos, missing imports, or minor style issues

### Why this matters

The `anti-patterns.md` skill is tagged `[always]` and injected into every subagent call. Adding a pattern there means the model is explicitly told not to do it on all future generations. The system gets smarter with every review cycle.
