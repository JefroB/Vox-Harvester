## Patterns Identified from local-coder-issues.txt Not Yet Covered by Scaffolding

## 1. Invalid Hypothesis API Usage

**Occurrences:** test_stats_parsing.py (Property 8)
**Failure mode:** Model invents non-existent Hypothesis functions (e.g., using
re.compile().match as a strategy, calling a strategy() function that doesn't exist).
**Root cause:** The model's training data includes outdated or incorrect Hypothesis API
knowledge. It confuses Hypothesis strategy composition patterns.

**Current scaffolding coverage:** property-test-skeleton.md shows basic @given,
@settings, and common strategies (st.integers, st.text, st.lists). However, it does
NOT demonstrate:
- st.from_regex (for regex-based generation)
- st.composite (for building custom strategies)
- st.builds (for constructing dataclasses/objects)
- st.one_of / st.just / st.none (for union types)
- st.fixed_dictionaries / st.from_type

**Proposed template:** `test-patterns/hypothesis-advanced-strategies.md`
- Tags: [test, property, hypothesis, strategy]
- Content: Complete reference of available Hypothesis strategies with correct syntax
- Priority: 15 (high — directly addresses the most common API misuse)

## 2. Uncontrolled Randomness in Threshold/State Tests

**Occurrences:** test_warning_lifecycle.py (Property 12)
**Failure mode:** When testing threshold-crossing behavior, the model generates
purely random data instead of constructing deterministic sequences that guarantee
the threshold is crossed. Test becomes flaky or untestable.
**Root cause:** Model doesn't understand that PBT for stateful invariants requires
CONTROLLED construction of inputs, not fully random data.

**Current scaffolding coverage:** property-test-skeleton.md shows basic property
structure but doesn't demonstrate stateful testing or controlled sequence generation.

**Proposed template:** `test-patterns/hypothesis-stateful-testing.md`
- Tags: [test, property, hypothesis, stateful]
- Content: Patterns for:
  - Building sequences that guarantee state transitions
  - Using st.lists with element strategies that control outcomes
  - Testing threshold crossings with deterministic prefix + random suffix
  - Hypothesis stateful testing with RuleBasedStateMachine
- Priority: 12

## 3. File Corruption from Parallel Writes

**Occurrences:** Tasks 2.1, 2.3, 2.4 (3 failures in one session)
**Failure mode:** When multiple local-coder calls target the same --output file in
parallel, they race and corrupt each other's output (truncation, garbage).
**Root cause:** Process-level issue — the orchestrator dispatches parallel subagents
that all call local_coder.py with the same output file simultaneously.

**Current scaffolding coverage:** None. This is an orchestration problem, not a
code generation problem. Scaffolding won't help.

**Proposed fix (NOT scaffolding — orchestrator logic):**
- The pre-task hook or orchestrator should detect when multiple parallel tasks
  target the same file and serialize them (run sequentially, not parallel).
- Alternatively, each parallel task writes to a temp file, and a merge step
  combines them.
- Add to .kiro/steering/ as a rule: "Never dispatch parallel local-coder calls
  targeting the same --output file."

## 4. Garbage/Truncated Output

**Occurrences:** Task 2.3 (22 tokens of garbage)
**Failure mode:** Model produces an extremely short, incoherent response instead
of the requested implementation. Likely caused by context corruption from the
parallel write race (file was empty/corrupted when --context pointed to it).
**Root cause:** The --context file was being overwritten by another parallel task
at the moment this task read it, resulting in garbage context → garbage output.

**Current scaffolding coverage:** None. Same root cause as #3 above.

**Proposed fix:** Same as #3 — prevent parallel writes to the same file.
Additionally, the review loop should detect <50 token outputs as automatic
failures and retry (or escalate to cloud) without counting as a "fix iteration."

## 5. Missing Conditional/Fallback Logic in Requirements

**Occurrences:** Task 1.1 (missing-fallback-warning-logic)
**Failure mode:** Model implements the "happy path" correctly but omits conditional
branches specified in requirements (e.g., "warn to stderr if X, then fallback to Y").
**Root cause:** When requirements have multiple fallback layers (try A → warn + try B
→ error), the simple model tends to implement only the first and last, skipping middle
warning/fallback branches.

**Current scaffolding coverage:** error-handling-strategy.md covers error hierarchy
but NOT multi-step fallback chains with warnings at each level.

**Proposed template:** `strategy-libraries/fallback-chain-pattern.md`
- Tags: [code, error, fallback, strategy]
- Content: Pattern showing multi-layer resolution with warnings:
  1. Try primary source → success = return
  2. Primary fails → warn to stderr with context → try fallback
  3. Fallback fails → warn again → try final fallback
  4. All fail → fatal error with actionable message
- Priority: 8

## 6. Empty/Stub Content for Prose-Heavy Templates

**Occurrences:** Task 5.4 (error-handling-strategy with empty bodies)
**Failure mode:** When asked to generate a template that is primarily prose/guidance
(not code), the model produces valid frontmatter but empty or stub section bodies.
**Root cause:** The simple model (qwen2.5-coder:7b) is optimized for code generation,
not prose writing. When the task says "include strategy guidance," it produces headers
but no substance.

**Current scaffolding coverage:** None specific to prose/documentation generation.

### Proposed Fix: Two-Pass Prose+Code Pipeline

For tasks that produce mixed prose and code (strategy docs, READMEs with examples,
templates with both explanation and implementation), use a TWO-PASS approach:

**Pass 1 — Prose (qwen3:8b, ~100 tok/s):**
- Generate the prose sections: headings, explanations, decision frameworks, guidance
- The prose model is fast and fluent at natural language
- Output: markdown with prose filled in, code blocks left as `TODO` placeholders

**Pass 2 — Code (qwen2.5-coder:7b or qwen3-coder:30b):**
- Take the prose output as --context
- Fill in the code blocks, examples, and implementations
- The code model sees the surrounding prose for context on WHAT to implement

### Guardrails Against Prose Model Hallucination

The prose model (qwen3:8b) hallucinates project details. These guardrails prevent
false claims from landing in the output:

1. **No project references in prose prompt:**
   - Strip any mention of specific file paths, function names, or module names
     from the prose model's task description
   - The prose model should generate GENERIC guidance, not project-specific claims
   - Example: "Write error handling guidance for Python apps" NOT "Write guidance
     for our local_coder/error_handler.py module"

2. **Code model validates technical claims:**
   - Pass 2 receives the prose output + actual project context files
   - If the prose says "use the retry decorator from utils.py" but that doesn't
     exist, the code model (which HAS --context) will generate the correct import
   - The code model acts as a factual grounding layer

3. **Prohibited content in prose pass:**
   - No import statements
   - No file path references (use placeholders like `<your-module>`)
   - No function signatures claiming to match existing code
   - No version numbers or dependency names without --context verification
   - Enforced by: prompt instruction + post-generation grep for banned patterns

4. **Structural contract between passes:**
   - Prose pass outputs markdown with fenced code blocks containing only:
     `# TODO: <description of what code goes here>`
   - Code pass replaces each TODO block with real implementation
   - This prevents the prose model from generating broken/hallucinated code

5. **Fallback escalation:**
   - If the prose model output contains >3 banned patterns (imports, file paths,
     specific function names), abort and escalate to cloud-only
   - This catches cases where the prompt leaked project details despite guardrails

### Implementation Sketch

```
# Two-pass generation for mixed prose+code tasks
def generate_mixed_content(task, context_files, output_path):
    # Pass 1: Prose (fast, fluent, no project context)
    prose_prompt = sanitize_for_prose(task)  # strip project-specific refs
    prose_output = call_local_coder(
        task=prose_prompt,
        complexity="prose",  # routes to qwen3:8b
        # NO --context (prevents hallucination about project)
    )

    # Validate: check for hallucination signals
    if contains_banned_patterns(prose_output):
        escalate_to_cloud(task)
        return

    # Pass 2: Code (slower, accurate, has project context)
    code_prompt = f"Fill in the TODO code blocks in this document: {prose_output}"
    final_output = call_local_coder(
        task=code_prompt,
        complexity="simple",  # or "complex" based on code difficulty
        context=context_files,  # real project files for grounding
        output=output_path,
    )
    return final_output
```

### When to Use Two-Pass vs Single-Pass

| Content type | Approach |
|---|---|
| Pure code (functions, classes, tests) | Single-pass code model |
| Pure prose (user-facing copy, translations) | Single-pass prose model (with guardrails) |
| Mixed (strategy docs, annotated examples, READMEs) | Two-pass: prose → code |
| Technical docs referencing actual code | Cloud-only (too risky for hallucination) |

### Detection Keywords for Two-Pass Routing

Trigger two-pass when task description contains:
- "strategy" + "example" or "code snippet"
- "documentation" + "implementation"
- "template" + "guidance" + "pattern"
- "README" + "usage example"
- Any task producing .md files with both prose sections AND code fences

## 7. Hypothesis + tempfile Conflict Pattern

**Occurrences:** Noted in test_append_invariant.py success notes — model correctly
used tempfile.TemporaryDirectory instead of pytest's tmp_path fixture.
**Pattern:** Hypothesis @given doesn't work with pytest fixtures (tmp_path).
Tests needing filesystem must use tempfile directly inside the test function.

**Current scaffolding coverage:** property-test-skeleton.md does NOT mention this
conflict or show the tempfile workaround.

**Proposed update to existing template:** `test-patterns/property-test-skeleton.md`
- Add a "Common Pitfalls" section:
  - "Do NOT use pytest fixtures (tmp_path, capsys) with @given — use
    tempfile.TemporaryDirectory() inside the test function instead"
  - Show correct pattern: `with tempfile.TemporaryDirectory() as td:`
